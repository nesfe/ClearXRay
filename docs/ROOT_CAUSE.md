# Причина Поломки

Этот документ фиксирует не общие рассуждения, а то, что было проверено на реальном сервере.

## Главный Лабораторный Вывод

> **Проблему ломал `flow=xtls-rprx-vision`.**

Это подтверждено чистым A/B-тестом.

### A/B-тест

#### Вариант A: рабочий baseline

- порт: `443`
- `VLESS + REALITY`
- `network=raw`
- без `flow`
- `sni=www.mix.com`
- новый `UUID`
- новый `pbk/password`
- новый `shortId`

Результат:

- подключение есть;
- трафик идёт;
- YouTube открывается.

#### Вариант B: тот же baseline + только `Vision`

- порт: `9443`
- тот же сервер
- тот же `UUID`
- тот же `pbk/password`
- тот же `shortId`
- тот же `SNI`
- тот же клиент
- единственное важное отличие:
  - `flow=xtls-rprx-vision`

Результат:

- таймаут;
- соединение нерабочее.

### Что это означает

На этом сервере и с этим клиентом:

- `REALITY` без `Vision` работает;
- `REALITY` с `Vision` не работает.

Это уже не гипотеза, а установленный практический факт.

## Что было доказано до A/B-теста

### 1. Сервер был жив

Было подтверждено:

- `22/tcp` открыт;
- `443/tcp` открыт;
- `xray` запущен;
- `ufw` активен;
- сервис слушал порт.

Следовательно, проблема была не в том, что VPS выключен или `xray` не поднялся.

### 2. Старая конфигурация ломалась на уровне REALITY-handshake

Логи сервера содержали:

- `REALITY: processed invalid connection ... failed to read client hello`

Это означает:

- TCP до сервера доходил;
- ошибка происходила до начала нормальной прокси-сессии;
- сервер не принимал присланный handshake как валидный `REALITY`-клиент.

### 3. После упрощения конфигурации трафик снова пошёл

После сборки минимального baseline:

- `Hiddify` подключился;
- внешний IP стал виден;
- трафик пошёл.

Следовательно:

- сам VPS способен обслуживать рабочий VPN;
- сам `Xray REALITY` на этом сервере способен работать;
- проблема была внутри старой конфигурационной ветки.

## Что именно отличалось между нерабочим и рабочим состоянием

### Старый проблемный конфиг

- несколько inbound'ов;
- часть из них с `flow=xtls-rprx-vision`;
- `mix.com`;
- старый credential-набор.

### Новый рабочий baseline

- один inbound;
- без `flow`;
- `www.mix.com` в `target`, `serverNames` и клиентском `sni`;
- новый credential-набор.

## Почему важен именно `Vision`

Без A/B-теста можно было сказать только:

- "скорее всего, мешал `Vision`";
- "возможно, мешал не только он".

После A/B-теста формулировка уже жёстче:

> при прочих равных добавление `flow=xtls-rprx-vision` ломает рабочую конфигурацию.

То есть именно `Vision` здесь был тем переключателем, который переводил конфиг из рабочего состояния в нерабочее.

## Что такое `Vision` технически

`Vision` — это режим `flow` для `VLESS`.

Он:

- не нужен для того, чтобы `REALITY` в принципе работал;
- меняет способ работы соединения после базового установления сессии;
- требует совместимости между серверным `Xray`, клиентом и конкретным сетевым путём.

Практический смысл для этого кейса:

- `REALITY` сам по себе у тебя работает;
- не работает именно связка `REALITY + flow=xtls-rprx-vision`.

## Почему раньше могло работать, а потом перестало

Возможные технические причины:

- обновился клиент;
- обновился `Xray`;
- изменилась совместимость реализации `Vision`;
- изменилась сетевая среда, в которой baseline без `Vision` ещё проходит, а `Vision`-ветка уже нет.

Что важно:

точный внешний триггер может остаться неизвестным, но причинный переключатель в конфиге уже найден.

## Что НЕ надо теперь делать

Не надо:

- возвращать `flow=xtls-rprx-vision` "на всякий случай";
- одновременно менять `SNI`, `UUID`, `pbk`, порты и клиента;
- лечить рабочий baseline новыми сложными параметрами.

## Практический итог

Если нужна рабочая конфигурация:

- использовать `VLESS + REALITY` без `Vision`;
- держать один inbound;
- держать один hostname;
- регенерировать credential-набор при полном пересборе;
- не смешивать baseline и экспериментальные ветки.
