# Причина отказа конфигурации с `flow=xtls-rprx-vision`

Документ фиксирует технический результат, полученный на реальном сервере при сравнении рабочей и нерабочей конфигураций `Xray REALITY`.

## Исходные условия

До пересборки сервер отвечал по сети, `xray` был запущен, порт `443/tcp` слушал соединения. Следовательно, проблема не сводилась к отказу VPS, остановке службы или закрытому сетевому порту.

В логах `xray` во время неуспешных подключений наблюдались сообщения вида:

- `REALITY: processed invalid connection ... failed to read client hello`

Это означает, что:

- входящее TCP-соединение доходило до процесса `xray`;
- ошибка происходила на этапе обработки начального `ClientHello` и проверки параметров `REALITY`;
- до штатной рабочей прокси-сессии соединение не доходило.

## Метод проверки

Причина отказа была изолирована через A/B-сравнение.

### Вариант A: рабочая конфигурация

- `VLESS + REALITY`
- `network=raw`
- `type=tcp`
- порт `443/tcp`
- без параметра `flow`
- `SNI = www.mix.com`

Результат:

- клиент подключается;
- внешний IP меняется;
- прикладной трафик проходит.

### Вариант B: та же конфигурация, но с `flow=xtls-rprx-vision`

Параметры, сохранённые без изменений:

- сервер;
- IP-адрес;
- клиент;
- `UUID`;
- `pbk`;
- `shortId`;
- `SNI`;
- базовая схема `VLESS + REALITY`.

Изменённый параметр:

- добавлен `flow=xtls-rprx-vision`

Результат:

- соединение не устанавливает рабочую сессию;
- клиент получает таймаут.

## Вывод

Для данной серверной конфигурации, клиентского приложения и сетевого маршрута воспроизводимо установлено следующее:

- базовая конфигурация `VLESS + REALITY` без `flow` работоспособна;
- добавление `flow=xtls-rprx-vision` переводит ту же конфигурацию в нерабочее состояние.

Это означает, что причиной отказа является не весь стек `Xray` и не `REALITY` как таковой, а именно ветка конфигурации, использующая `flow=xtls-rprx-vision`.

## Почему переустановка системы не устраняла проблему

Переустановка операционной системы не меняет семантику транспортного режима.

Если после пересборки сервера снова разворачивается конфигурация:

- `VLESS`
- `REALITY`
- `flow=xtls-rprx-vision`

то на новой системе воспроизводится тот же транспортный сценарий, который уже показал отказ. В этом случае чистая ОС устраняет накопленный конфигурационный мусор, но не устраняет причину, если она заложена в самом режиме передачи.

## Почему это могло перестать работать после длительного стабильного периода

Для таких конфигураций возможны изменения, не связанные с ручным редактированием JSON-файла:

- обновление клиентского приложения;
- обновление встроенной версии `Xray-core` у клиента;
- обновление серверной версии `Xray-core`;
- изменение сетевой среды или поведения фильтрации на маршруте;
- изменение совместимости реализации режима `xtls-rprx-vision`.

По результатам проведённой проверки невозможно однозначно назвать внешний триггер, который изменил поведение. Однако причинный параметр внутри конфигурации установлен: отказ воспроизводится при использовании `flow=xtls-rprx-vision` и исчезает при возврате к базовой конфигурации без `flow`.

## Практическая рекомендация

Если задача состоит в получении воспроизводимо рабочей конфигурации, рекомендуется:

- использовать `VLESS + REALITY` без параметра `flow`;
- поддерживать один inbound на одном публичном порту;
- использовать один hostname в `target`, `serverNames` и клиентском `sni`;
- регенерировать `UUID`, ключевую пару и `shortId` при полной пересборке;
- не смешивать рабочую конфигурацию и экспериментальные параметры в одном наборе.
